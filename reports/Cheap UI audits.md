# Cheap UI audits

**I would build an audit that finds and proves a small number of consequential problems per change.** Your history supports a cheap way to catch a broken hover corner, a disappearing filter menu, or an animation that skips directly to its endpoint. It also contains a real example of an agent challenging a whole page's premise and suggesting a structure you preferred. Those successes depended on different evidence. A still can show the corner. Understanding Friends required knowing what a student wants to find out. My recommendation is to spend your first five-hour subscription window testing whether a short task description, the right states, and one capable reviewer beat your existing screenshot review in **owner minutes per verified fix**. There is enough evidence to justify that experiment. There is no measured end-to-end result yet that justifies putting a council on every change.

## Reuse design reasoning by changing the evidence

**Kole's best contribution is a pair of examples on which the right answer reverses.** Repeating an email in a single-account menu can waste space. The same line in a multi-login workspace switcher tells a person which account owns the next group of workspaces. A three-dropdown date form looks simple until the task is “next Friday.” A calendar-only picker can make a known birthday decades ago painful. A project link shortens a trip from a task but still interrupts the work. A small preview can answer the immediate question without losing the task. Convert each example into a question, the condition under which it matters, and a legitimate exception. Retrieve one relevant example when a case calls for it. Sending the entire archive on every audit would make imitation easy and transfer hard to measure. A note widget already used the competing-gesture lesson before the visual archive was assembled. Nested links navigate, double-clicking the title or body selects the right editor, and an explicit Edit action provides a keyboard/touch route. Those behaviors give a small test a clear pass condition. [Jain's marked examples](/Users/sreysus/workflow/ia-app/.local/kole-jain/visuals/INDEX.md) · [Note widget](/Users/sreysus/workflow/ia-app/apps/web/src/components/dashboard/widgets/NoteWidget.tsx:49)

There are several credible explanations for the misses. **Perception** fails when a one-pixel difference disappears on a downscaled page. **Attention and reporting** fail when the reviewer sees a feature and a brief persuades it to dismiss it. **Coverage** fails when a neutral desktop capture omits open menus, phone passing periods or animation. **Intent** is underdetermined when the same picture is right for one role or job and wrong for another. **Repair** fails when one corrected symptom creates a neighboring regression. Models need not have been trained exclusively on text for any of this to happen. Multimodal models have documented image training. The local experiments cannot identify the training cause for these particular model versions. Sutton's argument about scalable search and learning is compatible with measuring a specific behavior at today's fixed budget. A useful challenge to our own elaborate pipeline is to let each stronger general model compete against it on the same held-out cases. [Gemini technical report](https://deepmind.google/gemini/gemini_1_report.pdf) · [Rich Sutton, The Bitter Lesson](https://bitterlesson.org/)

Outside work suggests which bets deserve an experiment. **UICrit** tested expert design comments and task/visual example retrieval. Across the small expert study, mean comment quality rose from 0.31 to 0.48, while human comments scored 0.75. That is evidence for trying a relevant exemplar, with an important gap to human feedback. **DiffSpot** gave 13 models controlled web image pairs, each changed in one localized CSS property or left identical. The best recovered 40.7% of true changes. **Scry's** practitioner benchmark used real reference/generated mobile pairs. Its highest-recall run matched 225 of 557 known issues and flagged 71 of 77 untagged controls. Untagged controls can contain genuine problems. These studies measured critique quality, visual difference detection and known defect localization respectively. None predicts a percentage of IA bugs you will catch. [UICrit](https://arxiv.org/html/2407.08850v1) · [DiffSpot](https://arxiv.org/abs/2605.29615) · [Scry Design Diff Eval](https://blog.scrymore.com/paper/)

**ReDeCheck** found 33 distinct responsive layout failures on 16 of 26 production pages by reasoning about element relationships across viewport widths. Many reports traced to one fault. **Spendesk** dealt with screenshot quota pressure by collecting the states and variants of a component into one snapshot story, keeping the useful comparisons visible. Both suggest paying for another state or viewport before paying for another opinion on the same image. **Theo's T3 Code redesign** shows a different viable approach. Comparing with real competing products exposed weak typography and hierarchy, and the project shipped concrete improvements. It took over 30 rounds. Theo estimated about $250 equivalent for the work shown at that point. A UI scored around 9 alone and 7.4 in a fresh comparative context, while an unchanged reference moved from 8.3 to 9.1. Borrow the comparisons and the fresh judge. His redesign is a weak basis for pricing a routine audit or stopping when a model awards a nine. ## What makes Jamik's audit log feel quieter

The [close-up comparison](/Users/sreysus/workflow/ia-app-archives/audit-table-closeups-20261123.html) puts native screenshot crops together for three reading tasks. IA's row and menu come from owner captures during the audit-table work. Its detail sheet is an October archive. Jamik's source is a cropped desktop composition viewed inside an X phone screenshot. ReUI's examples are rendered desktop demos. Differences within a capture are more trustworthy than absolute font sizes or CSS dimensions across captures. Motion and focus transitions require a recording.

- **Trace two events in the same minute.** In IA's 11:33 PM pair, the time, shield and “Report” match. The eye has to find “System / Created feedback GitHub …” versus “Rebanto Nath / Submitted report.” Ten of twelve visible events have the shield. It encodes the moderation category correctly, but on this slice it occupies the start of the most informative column while the action text gets clipped. In Jamik the actor slot changes from a gradient disc to a link glyph for a service. The tiny action dot changes separately. A revoked key and a denied request share a red dot while their complete verbs distinguish them. For IA I would free space for the verb and the specific record where a displayable identifier exists, then test whether a category marker still helps.
- **Read the ink inside one control.** Jamik's search is outlined on the page background. Nearby filters have a slight fill, a muted field name and a brighter value. A chevron follows “Anyone” and an × follows the applied action. Jamik gives the field, value and available operation one small area. IA's captured time menu distinguishes checked and highlighted rows, and the Fluid branch already renders removable active-filter chips. Its desktop design splits editing at the column and reading or clearing the selection in the chip row. ReUI's log gives the date range a visible value and the general filter a generic button. The question to test is whether an admin can explain the visible subset at a glance and change just one condition. - **Hold the data constant.** Jamik shows six distinct events over several days, a mixture of actors, compact action names and named targets. IA shows repeated system events in the same minute, generic record labels and longer natural-language actions. Re-render the exact IA pair in both treatments before attributing the improvement to typography or spacing. A valid result is that both versions still read poorly because neither identifies which report changed.

For a cheap recurring audit, keep a single reference row crop beside a crop of the candidate's densest real rows. Ask which values distinguish neighboring events, which marks repeat, and which distinguishing values get clipped. Require the reviewer to quote two actual rows. For redesign, change one feature at a time in the same data and ask which variant makes identifying the event easier and which one the owner would rather use. The first answer can be timed. The second teaches the owner's taste. They can differ.

## What the audit log rework taught

Implementing the Jamik comparison in IA took three owner review rounds, and each round found defects that code checks and agent screenshots missed. Examples: a popover that overflowed, a seam where two translucent buttons met, a hover highlight left in the wrong place by cached geometry, a page that shifted when a menu opened (caused by the preview harness, not the app), and filler text. The full log, with causes, fixes, screenshots and a list of cheap automated checks that would have caught each one, is in [audit-log.md](<../research_notes/Cheap UI audits/audit-log.md>). Most of those checks are deterministic DOM measurements, not model judgment, which supports splitting cheap audits into scripted geometry probes plus a small model pass for taste.
