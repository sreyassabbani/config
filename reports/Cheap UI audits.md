# Cheap UI audits

**I would build an audit that finds and proves a small number of consequential problems per change.** Your history supports a cheap way to catch a broken hover corner, a disappearing filter menu, or an animation that skips directly to its endpoint. It also contains a real example of an agent challenging a whole page's premise and suggesting a structure you preferred. Those successes depended on different evidence. A still can show the corner. Understanding Friends required knowing what a student wants to find out. My recommendation is to spend your first five-hour subscription window testing whether a short task description, the right states, and one capable reviewer beat your existing screenshot review in **owner minutes per verified fix**. There is enough evidence to justify that experiment. There is no measured end-to-end result yet that justifies putting a council on every change.

## Reuse design reasoning by changing the evidence

**Kole's best contribution is a pair of examples on which the right answer reverses.** Repeating an email in a single-account menu can waste space. The same line in a multi-login workspace switcher tells a person which account owns the next group of workspaces. A three-dropdown date form looks simple until the task is “next Friday.” A calendar-only picker can make a known birthday decades ago painful. A project link shortens a trip from a task but still interrupts the work. A small preview can answer the immediate question without losing the task. Convert each example into a question, the condition under which it matters, and a legitimate exception. Retrieve one relevant example when a case calls for it. Sending the entire archive on every audit would make imitation easy and transfer hard to measure. A note widget already used the competing-gesture lesson before the visual archive was assembled. Nested links navigate, double-clicking the title or body selects the right editor, and an explicit Edit action provides a keyboard/touch route. Those behaviors give a small test a clear pass condition. [Jain's marked examples](/Users/sreysus/workflow/ia-app/.local/kole-jain/visuals/INDEX.md) · [Note widget](/Users/sreysus/workflow/ia-app/apps/web/src/components/dashboard/widgets/NoteWidget.tsx:49)

There are several credible explanations for the misses. **Perception** fails when a one-pixel difference disappears on a downscaled page. **Attention and reporting** fail when the reviewer sees a feature and a brief persuades it to dismiss it. **Coverage** fails when a neutral desktop capture omits open menus, phone passing periods or animation. **Intent** is underdetermined when the same picture is right for one role or job and wrong for another. **Repair** fails when one corrected symptom creates a neighboring regression. Models need not have been trained exclusively on text for any of this to happen. Multimodal models have documented image training. The local experiments cannot identify the training cause for these particular model versions. Sutton's argument about scalable search and learning is compatible with measuring a specific behavior at today's fixed budget. A useful challenge to our own elaborate pipeline is to let each stronger general model compete against it on the same held-out cases. [Gemini technical report](https://deepmind.google/gemini/gemini_1_report.pdf) · [Rich Sutton, The Bitter Lesson](https://bitterlesson.org/)

Outside work suggests which bets deserve an experiment. **UICrit** tested expert design comments and task/visual example retrieval. Across the small expert study, mean comment quality rose from 0.31 to 0.48, while human comments scored 0.75. That is evidence for trying a relevant exemplar, with an important gap to human feedback. **DiffSpot** gave 13 models controlled web image pairs, each changed in one localized CSS property or left identical. The best recovered 40.7% of true changes. **Scry's** practitioner benchmark used real reference/generated mobile pairs. Its highest-recall run matched 225 of 557 known issues and flagged 71 of 77 untagged controls. Untagged controls can contain genuine problems. These studies measured critique quality, visual difference detection and known defect localization respectively. None predicts a percentage of IA bugs you will catch. [UICrit](https://arxiv.org/html/2407.08850v1) · [DiffSpot](https://arxiv.org/abs/2605.29615) · [Scry Design Diff Eval](https://blog.scrymore.com/paper/)

**ReDeCheck** found 33 distinct responsive layout failures on 16 of 26 production pages by reasoning about element relationships across viewport widths. Many reports traced to one fault. **Spendesk** dealt with screenshot quota pressure by collecting the states and variants of a component into one snapshot story, keeping the useful comparisons visible. Both suggest paying for another state or viewport before paying for another opinion on the same image. **Theo's T3 Code redesign** shows a different viable approach. Comparing with real competing products exposed weak typography and hierarchy, and the project shipped concrete improvements. It took over 30 rounds. Theo estimated about $250 equivalent for the work shown at that point. A UI scored around 9 alone and 7.4 in a fresh comparative context, while an unchanged reference moved from 8.3 to 9.1. Borrow the comparisons and the fresh judge. His redesign is a weak basis for pricing a routine audit or stopping when a model awards a nine. For **routine changes**, collect rest/open/selected/scrolled states plus one role or viewport that could invalidate the contract. Run assertions first. Send only an unexplained difference, a materially changed component without an accepted baseline, or a sampled unflagged case to one reviewer. A useful response names the actor, action, location, visible consequence, evidence ID, reproduction and a condition the repair must preserve. A zero-finding response is valid. Let a source-enabled reviewer inspect the relevant implementation only after recording the observed symptom. A patch earns credit when replay demonstrates the improvement and the named exception still passes. A structural idea becomes a design proposal with alternatives. Keep a small rotating review of unchanged flows because a consistently poor design can survive every diff.

For an occasional **product review**, ask a different question. For example, “An admin follows a thread link into #announcements, realizes the audience is wrong, checks the owning channel and returns to the same conversation. Where must they reconstruct their location? Give two ways to preserve it. Describe which frequent action each makes harder.” The reviewer can propose breadcrumbs without being cued to produce them. Give it a record of the route, real alternatives and surviving state. For an editorial choice such as Chat versus Whiteboards as peer tabs, measure what users try to find or ask the owner for a blinded A/B preference. A simulated click count alone cannot establish the frequency or value of the task.

For a **bounded finder**, try this input on the admin table. “You are auditing an admin who needs to filter by two people and inspect one event without losing their place. Here are the initial state, actions, resulting states and visible controls. Report at most three distinct obstacles supported by this record. For each, name the earliest failing step, what the admin can observe, the smallest check that would settle the diagnosis, and one behavior a repair must preserve. Return an empty list if the task works. Put structural alternatives in a separate paragraph with the tradeoff.” For an independent discovery trial omit the expected defect, owner annotations, answer key and fixed capture. Reproduction and repair stages can see the expected outcome once discovery is scored.

## The experiment should be able to retire the proposed automation

Freeze the panel, known table examples, GWC screenshots and original Snake complaints as **development cases**. Find fresh natural changes from other components or later revisions, plus deliberately retained designs. Split by component or flow so near-identical states cannot cross between development and evaluation. Include a phone case, a keyboard case, a temporal case and an information-architecture job. Have the owner briefly mark visible issues and important tasks before seeing model answers. Keep their answers private. Blind candidate provenance during adjudication. Review new model discoveries individually and record “valid but not worth fixing,” “preference,” “incorrect” and “insufficient evidence” separately. An incomplete human list makes exact overall recall unknowable.

Compare three paths on identical cases inside the budget. **A** runs only the deterministic checks. **B** adds one capable direct reviewer. **C** gives that same model the task and compact state evidence plus one retrieved Jain comparison. To isolate what helped, run the evidence packet alone against packet-plus-example before drawing a retrieval conclusion, holding source access, effort and image size fixed. A same-length irrelevant example tests whether retrieval simply primes the model to complain. Reverse the valid account context while keeping the same menu pixels. A reviewer that recommends deleting the email in both cases may have learned a style preference instead of its rationale. For a proposed structural repair, show the owner unlabeled renders in randomized order and include “keep current.” If budget permits, try a focused cheap visual pass and measure only the additional accepted findings. Keep repeats for estimating variability on a subset. Score blind discovery separately from what happens after the true region is pointed out. That distinction tells you whether investing in better capture, better judgment or better repair could pay off.

The primary decision is **verified unique fixes per owner hour within one subscription window**. Log time to first actionable issue, false alerts per apparently clean change, known consequential misses including uncaptured states, regressions introduced per attempted patch, weekly quota and wall time. Sample some silent cases at random, then report misses by state and severity. Compare human labeling, dismissals and rework with the time the owner would otherwise spend on the same changes. Report small-sample counts alongside rates. Keep an extra pass only if its incremental accepted fixes save owner time or catch a predeclared serious failure class. If examples increase imitation, retire retrieval from routine runs. If the cheap reviewer adds little over measurable contracts, keep the checks and spend the occasional full window on the design question a deterministic test cannot answer. That would be a successful outcome of the research.
